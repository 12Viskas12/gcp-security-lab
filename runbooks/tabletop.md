# Tabletop-упражнение и критерии эскалации

## Сценарий

SOC L1 получает алерт `SEC | Cloud Storage PERMISSION_DENIED` от `sa-no-access`, затем `SEC | Service account token generated (impersonation)`. В Data Access видно чтение `confidential/finance-report-SYNTHETIC.csv` identity, которая раньше его не читала. Данные синтетические, но разбираем как реальные (CONFIDENTIAL).

Формат: учебный разбор с переключением ролей (L1, L2, Cloud Security Engineer, Incident Commander).

## Ход упражнения

| Время (T+) | Событие / вброс | Действие | Роль |
| --- | --- | --- | --- |
| 0 мин | Приходит алерт D-05 | L1 открывает инцидент, фиксирует время | L1 |
| 5 мин | Приходит алерт D-06 | L1 связывает два алерта по identity и времени | L1 |
| 15 мин | Найдено успешное чтение CONFIDENTIAL | Эскалация к L2 | L1 → L2 |
| 30 мин | Принципал, выпустивший токен, неизвестен | L2 проверяет TokenCreator, IP, user agent; эскалация к Cloud Security Engineer | L2 → CSE |
| 45 мин | Подтверждён доступ к CONFIDENTIAL | CSE ограничивает доступ (containment), IC принимает решение об уведомлении | CSE, IC |
| 90 мин | Причина найдена | Eradication и Recovery | CSE |

## Ответы на вопросы задания

| Вопрос | Ответ |
| --- | --- |
| 1. Кто принимает инцидент? | SOC L1 на дежурстве. В лабе: владелец проекта в роли L1. |
| 2. Какие логи проверяются первыми? | Admin Activity (изменения IAM/SA), затем Data Access Storage по объекту и identity, `iamcredentials` (кто выпускал токен), `serviceAccountDelegationInfo`. |
| 3. Как устанавливается scope? | Все действия принципала ±1 час; все объекты, прочитанные identity; были ли изменения IAM до события; другие SA с тем же TokenCreator. |
| 4. Когда требуется ограничить доступ? | Если identity неизвестна/неожидаема, затронут CONFIDENTIAL, есть успешное чтение вне процесса — немедленно (отозвать TokenCreator, отключить SA). Для единичного отказа — наблюдение. |
| 5. Какие доказательства сохранить? | Сырые логи с хешем, IAM-политики до/после, письма алертов, скриншоты, список команд ([incident-response.md](incident-response.md), п.2). |
| 6. Кто принимает решение о восстановлении? | Владелец сервиса совместно с Cloud Security Engineer, после проверки `verify.sh` и закрытия причины; IC утверждает при CRITICAL. |
| 7. Как документируются результаты? | `incidents/incident-0X.md` (10 пунктов), протокол tabletop (раздел ниже), запись в `reports/final-report.md`. |

## Критерии эскалации

| Переход | Критерий |
| --- | --- |
| SOC L1 → SOC L2 | Алерт не объясняется плановым изменением; затронут CONFIDENTIAL; ≥2 связанных алерта по одной identity за 30 минут; успешный доступ после серии отказов. |
| SOC L2 → Cloud Security Engineer | Нужно изменить IAM/политику/сеть для containment; подозрение на компрометацию identity; слепое пятно детекта (аудит ослаблен); причина не очевидна за 60 минут. |
| Cloud Security Engineer → Incident Commander | Подтверждена утечка CONFIDENTIAL; аудит отключён/ослаблен у привилегированной identity; затронуто больше одного проекта/сервиса; требуется уведомление третьих лиц. |

## Выводы разбора

- Корреляция двух алертов по одной identity и времени делается вручную: автоматической корреляции нет.
- Успешное чтение CONFIDENTIAL неожиданной identity алерта не вызывает (D-08): слепое пятно, закрывается метрикой по объекту и identity.
- Каналы связи ограничены email: нет on-call интеграции и ChatOps.
- Эскалация и критерии определены выше; решение о восстановлении принимает владелец сервиса после проверки `verify.sh`.
